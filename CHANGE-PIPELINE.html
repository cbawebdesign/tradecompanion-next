Justin's Change Pipeline

How Justin goes from “this is wrong” to a merged, deployed fix — and what has to exist first so a merge can't take down his own trading screen.

DRAFT · 2026-08-25/ cbawebdesign/tradecompanion-next/ supersedes AGENT-INTAKE-PLAN §4

The situation

Justin has Cursor, he's on the repos, and he wants to make changes and take part in merges. That's a good outcome — he's the domain expert, and the round-trip through me for a color or a keyword list is pure overhead.

The problem is what's between his merge button and production. Right now: nothing. No CI, no tests, no automated type-check, and master auto-deploys to Vercel. A merge is live in his own terminal within about ninety seconds, and the app he's deploying into is the one he trades on.

So this plan is in two halves — build the floor, then hand him the keys. Doing the second without the first is how he ends up staring at a blank alert bar at 9:47am.

What's between a merge and production today

The good news is that next build already does more than people expect — it type-checks every file. A meaningful share of past regressions in this codebase were shape errors that TypeScript would have caught. Wiring that into CI is cheap and buys most of the protection.

Build the floor

Three things, all small, all before Justin gets write access. This is maybe half a day total.

1 — CI on every pull request

A single workflow running next build and next lint. Highest-leverage item on this page: it turns the type-checker from something someone might run into something that blocks a merge.

# .github/workflows/ci.yml
name: CI
on:
  pull_request:
    branches: [master]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm run build
2 — Branch protection on master

Require a pull request, require the CI check to pass, disallow force-push. Without this the workflow above is decorative — anyone can push straight past it.

3 — Confirm Vercel preview deploys are on for PRs

This is the piece that makes Justin genuinely productive rather than merely permitted. Every PR gets its own URL running that branch's code. He logs in with his own account, sees his change against live market data, and decides — all before anything touches master. Verify it's enabled; on the default Vercel + GitHub integration it is, but confirm rather than assume.

Three classes of change

Not all edits carry the same risk, and the difference isn't size — it's whether a mistake is visible. That's the line the tiers are drawn on, and they borrow the app's own connection-status colors on purpose.

TIER 1

Justin ships it himself

CI green → he merges
  • Copy, labels, tooltips, placeholder text
  • Alert type colors — lib/alertTypeColor.ts
  • Theme tile emojis and styling — components/ThemesPage.tsx
  • Default values he is the authority on: the PR blacklist firm list in lib/excludePrPatterns.ts, default excluded filing forms, default sound frequency and duration

No control flow. Every one of these is something he can see on the preview URL — if it looks right there, it is right. Worst realistic outcome is cosmetic and rolls back in seconds.

TIER 2

He opens the PR, you review

Approval required
  • A new Settings field, a new column, a new alert type
  • Render-path changes in a component
  • Themes page behavior — sorting, filtering, favorites
  • A new polling source or endpoint

These touch the store shape and the config type. The failure mode is usually loud (something looks broken) but not always — adding a config field without adding it to the sync path means it silently fails to persist, which looks fine until the next login.

TIER 3

Not without me, ever

Chris-only
  • hooks/useCosmosSync.ts — sync and restore
  • store/useStore.ts — addAlert / addAlerts dedup
  • lib/alertDedup.ts — the normalize and match-key logic
  • hooks/useSignalR.ts, hooks/useNewsHub.ts — alert ingestion
  • lib/marketCalendar.ts and the per-source since-window logic
  • Anything touching auth, identity, or userKey

Every item here has already caused a real incident: subscriptions wiped on re-login, watchlists orphaned on restore, the 5/19 previous-close bug that hid a whole session of news, duplicate PRs from a dedup key that didn't match. They share one property — they fail silently.

Why the tiers exist at all

A preview URL proves what appears. It cannot prove what failed to appear. Justin can open a preview, see alerts flowing, and merge a change that quietly dropped every filing for symbols starting with B — there is nothing on screen that says so. That asymmetry is the entire argument for Tier 3, and it's worth explaining to him in those words, because it isn't obvious and it isn't about trusting him.

The lifecycle of one change

01
Justin · Cursor

Describes the change on a branch named justin/short-description. Cursor's agent writes it; the committed rules files (below) tell it what it must not touch.

02
Automatic

Push opens a PR. CI runs lint and the type-checking build. A red check means the conversation stops here — no review needed, nothing to discuss.

03
Automatic

Vercel comments a preview URL on the PR.

04
Justin

Opens the preview, logs in as himself, works it against live data. This is the step that does the real verification — not the CI check.

05
Tier-dependent

Tier 1 — he merges. Tier 2 or 3 — it waits for me. The tier is stated in the PR description; if he isn't sure which it is, that itself means Tier 2.

06
Automatic

Merge to master ships to production.

07
Either of us

If it's wrong: roll back in Vercel first, diagnose second. Never debug forward on a live trading day.

The one hard rule

No merges to master during the session

09:15–16:15 ET on any trading day, master is frozen. Merge before the open or after the close. Everything else on this page is a preference that can be argued with; this one isn't. A bad deploy at 10:30am costs real money, and the rollback still means a reload in the middle of a move.

Preview URLs are exempt — he can test on a preview at any hour, which is most of what he'll want to do anyway.

Teaching Cursor the landmines Shipped

Cursor's agent is confident and fast, which is exactly the risk on a codebase whose failure modes are invisible. It reads rules files committed to the repo, so the tier list lives there rather than in Justin's head — and it applies to everyone automatically, with nothing to configure per person.

Cursor deprecated the single .cursorrules file in favour of a .cursor/rules/ directory of .mdc files, read recursively. Those are the primary system; AGENTS.md at the root carries the same guidance for any other tool, and doubles as a plain-English orientation if Justin just wants to understand how the app fits together.

FileScopeWhat it covers
AGENTS.mdRoot, all toolsOrientation, the danger list, every convention below. Written to be read by a person too.
00-architecture.mdcAlways onStack, directory map, which backends exist, the proxyUrl() rule for local CORS.
10-danger-zones.mdcAlways onThe Tier 3 files — each one named beside the incident it actually caused, with “propose, don't apply”.
20-alerts.mdchooks/ lib/ store/The ten alert types, dedupKey conventions, filtering, the inline-hex colour rule.
30-ui.mdccomponents/ app/The symbol invariant, theme variables, density, how pop-outs work.

The content is drawn from what has actually broken here, not from generic best practice. The rules that matter most:

  • Alerts fail silently — stated up front, as the thing to understand before anything else. A change that reduces the number of alerts shown is guilty until proven innocent.
  • Never “simplify” a filter, dedup check or date comparison — those conditions look over-complicated because each clause fixes a specific reported bug. Deleting one reads as a tidy-up in review.
  • Alert colours are inline hex, never Tailwind classes — the content scan doesn't cover lib/, so class names there get purged. This already shipped once and killed every colour except filings.
  • Every alert needs a dedupKey on the existing source:id shape, never built from Date.now().
  • Theme variables, not literal colours — five themes; a hardcoded hex looks right in the default and breaks the other four.
  • The symbol invariant — flag/unflag, right-click → watchlist, AHK fire. All three, every surface a ticker appears on.

Same files, adapted, belong in the other repos once this works here.

A better first move than commit access

Worth saying plainly: a large share of what Justin actually wants to change on a given day is a value, not code — a color, a keyword list, a threshold, an emoji. Much of that is already a Settings field, and most of the rest could be in an afternoon.

Every item moved into Settings or tc-admin is one he changes in five seconds with no branch, no CI, no review, no deploy, and no rollback risk. That is strictly better for both of us than a PR round-trip, and it drains Tier 1 down to nearly nothing.

So run this in parallel with the pipeline, and let the pipeline be for the things that genuinely are code.

Open questions

  1. Which four repos did you send him? I only have tradecompanion-next on this machine — the legacy app, TcIsolatedWorker and tc-admin aren't here, so I'm working from the session notes for those.
  2. Is branch protection already on master? Needs an admin token to check; mine is READ.
  3. Does Justin want merge rights, or just PR rights? Tier 1 assumes he can merge his own. If he'd rather you merge everything, the tiers still work — they just become review priorities instead of permissions.
  4. Your cousin — same tiers, or a different posture? Worth deciding before adding him rather than after.

Not doing

  • No auto-merge on green CI. A passing type-check is not evidence that alerts still fire.
  • No agent merging its own PR. A person clicks merge, every time.
  • No CI bypass for “small” changes. The small ones are where it gets skipped and where it bites.
  • No Cosmos issue-intake system. The April plan's TcIssues container, submit form and triage service are superseded — Cursor plus a GitHub issue does the same job with nothing to build or maintain.
